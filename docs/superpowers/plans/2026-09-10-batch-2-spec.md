# Batch 2 spec — MCP correctness fixes and full toolbar coverage

The requirements for the next development batch. Four plans implement this spec;
each names it as its `**Spec:**`.

**Where the findings come from:** `2026-09-10-testing-session-bugs.md` in this
directory (items T1–T6), produced by driving the slicer over MCP with the user on
2026-09-10. Read it — it carries the reproductions.

**Decided with the user (2026-09-10):** full toolbar coverage before release, and
painting gets region selection and read-back, not just bands.

---

## Global Constraints

Every task in every plan inherits these.

- **Branch:** `sync-upstream-2.5`. Do not push. Do not create branches.
- **Commit style:** `fix:` / `feat:` + what changed, past tense. The body names the
  **root cause**, not the symptom, and lists related occurrences checked —
  *including the ones deliberately left alone, and why*. Read `git log -5` for the
  bar. Every commit ends with:
  `Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>`
- **Threading:** every tool handler body runs inside `run_on_main_thread()`
  (`OrcaMCPCommon.hpp`). Anything touching `Model`, `Plater` or the preset bundle
  must be inside it. A modal opened inside it hangs the GUI forever.
- **Dialogs:** never call `set_mcp_dialog_suppression()` directly. `McpDialogSuppressionGuard`
  (RAII, nest-safe) is the only sanctioned way.
- **Pure logic goes in a free function with Catch2 coverage** under
  `tests/slic3rutils/`. This project tests logic without a printer wherever
  possible; geometry maths must be testable without a GUI.
- **Undo/redo:** any tool that mutates the model must call
  `plater->take_snapshot(<description>)` **before** mutating, so `undo` works.
  **Do NOT copy `move_object`** — corrected 2026-09-10: it takes no snapshot at
  all. The whole MCP layer contains exactly two `take_snapshot` calls,
  `OrcaMCPServer.cpp:4080` (`set_object_printable`) and
  `OrcaMCPFilamentUtils.cpp:151`. **`set_object_printable` is the pattern to
  follow.** The missing snapshots on the existing tools are logged as T7 and are
  not your job unless your plan says so.
- **Registration:** tools are registered with `register_tool({...})` in
  `register_builtin_tools()` (`OrcaMCPServer.cpp`) or the per-area registrars
  (`OrcaMCPFilamentTools.cpp`, `OrcaMCPPrinterTools.cpp`). New tool groups get
  their own file following that pattern, added to `src/slic3r/CMakeLists.txt`.
- **Docs:** every new or changed tool updates `docs/tools/reference.md`, and the
  tool table plus the count in `CLAUDE.md`. The count command is in CLAUDE.md.
- **Response shape:** `{"status": "success"|"error"|"partial", ...}` plus
  `active_warnings` on anything that mutates the scene, matching existing tools.
- **Verify before reporting:**
  ```
  cmake --build build/arm64 --config RelWithDebInfo --target OrcaSlicer slic3rutils_tests -- -j8
  build/arm64/tests/slic3rutils/RelWithDebInfo/slic3rutils_tests.app/Contents/MacOS/slic3rutils_tests
  ```
  Baseline at the time of writing: **174 cases / 1195 assertions / 0 failures**.
  The skipped count varies run to run (bundled-Python and numpy cases) — that is
  expected, not a regression.
- **Do not start the app or contact the printer** unless the plan says to.

## Plan 1 — Correctness fixes (T1–T4)

The four defects found during the session. Full reproductions are in the findings
doc; the requirements are:

1. **T1 — `apply_config` must accept a JSON array for list-typed keys.**
   `get_valid_config_keys` advertises types `strings`/`ints`/`bools`/`floats`; a
   caller passing an array for one is currently rejected with no explanation. Accept
   arrays (join with `;` before deserialising) and keep accepting the joined string.
   Separate the failure signals: "unknown key" and "value not accepted" must be
   distinguishable in the response, and the latter must say what shape was expected.
   Sweep the sibling paths (`set_object_config`, and the `print`/`filament`/`printer`
   branches).
2. **T2 — `get_presets` must be answerable without a filter.** Even at
   `summary: true` the unfiltered response is ~54,600 characters, over an MCP
   client's per-result limit. Cap the default and report the true total with a hint
   naming the filter parameters. Separately, establish whether a stale cached tool
   schema survives an app update — if the bridge caches, fix it; if it is the
   client, document it in the upgrade notes.
3. **T3 — the bridge must not report a running app as "not running."** Under a burst
   of 8 concurrent calls, `scripts/orcamcp-bridge.py` returned "OrcaMCP is not
   running" while the process was alive and answering. Distinguish connection-refused
   (really down) from timeout/busy, and give advice that matches.
4. **T4 — `suggest_color_mix` must not report an exact match as an error.** When the
   target equals a loaded filament, return `status: "success"` with a single-component
   recipe (that slot, ratio 100), `delta_e: 0` and `exact_match: true`.

**Also from the session, same area:** `suggest_color_mix` and `get_color_palette`
should mark an out-of-gamut result rather than returning a confident recipe at
ΔE 54. Add a gamut marker with a documented threshold.

## Plan 2 — Painting (T5, and 4 of the missing gizmos)

**The mechanism.** `ModelVolume` carries four `FacetsAnnotation` members
(`src/libslic3r/Model.hpp:875-884`): `supported_facets`, `seam_facets`,
`mmu_segmentation_facets`, `fuzzy_skin_facets`. All four are the same type, so one
tool with a `mode` parameter covers all four.

Write path, verified:
- `TriangleSelector::set_facet(int facet_idx, EnforcerBlockerType state)`
  (`TriangleSelector.hpp:361`) — the per-facet primitive.
- `FacetsAnnotation::set(const TriangleSelector&)` (`Model.hpp`) — commits it.
- `FacetsAnnotation::get_facets(...)`, `has_facets(...)`, `reset()` — read/clear.

**`paint_object`** — required capability:

- `mode`: `color` | `support` | `seam` | `fuzzy_skin`. Selects which annotation
  member is written. For `color`, the state encodes the filament slot; for the
  others it is enforcer/blocker.
- **Bands along an axis:** `{axis: "x"|"y"|"z"}` with either an even split across a
  list of filaments, or explicit `[{filament, from, to}]` ranges in object
  coordinates. A facet belongs to the band containing its centroid.
- **Region selection:** paint inside a box or a sphere given in object coordinates.
- **Read-back:** report what is currently painted, so an agent can verify its own
  work. This is a separate concern and may be its own tool (`get_object_paint`) if
  that reads better.
- Clearing: a documented way to reset an annotation.

Coordinates must be unambiguous — state in the tool description and in
`reference.md` whether ranges are object-local or plate coordinates, and be
consistent with what `get_object_info` reports.

**Also in this plan:** `set_brim_ears` — brim ears are **not** facets. They are
`BrimPoints brim_points` on `ModelObject` (`Model.hpp:390`), a different mechanism,
so a small separate tool.

**Acceptance:** the session's original request must work — the print-bed scraper
(40 x 122 x 6 mm, lying flat, length along Y) painted in 14 even bands along Y from
the scraping edge to the hanging hole, using mixed filament slots 5–18.

## Plan 3 — Mesh editing

- **`split_object`** — both `splitobjects` and `splitvolumes` from the toolbar.
  APIs exist: `ModelObject::split(ModelObjectPtrs* new_objects, bool remap_paint)`
  (`Model.hpp:521`) and `ModelVolume::split(unsigned int max_extruders, bool remap_paint)`
  (`Model.hpp:946`). Note `remap_paint` — decide and document what happens to
  existing paint, and say so in the response.
  This one matters beyond itself: `set_object_filament` already takes a `volume_id`,
  but nothing can currently produce parts to address.
- **`boolean_object`** — union / difference / intersection via
  `namespace MeshBoolean` (`src/libslic3r/MeshBoolean.hpp`).
- **`simplify_object`** — mesh decimation. The gizmo is `GLGizmoSimplify`; locate the
  algorithm it calls and drive that directly rather than the gizmo.
- **`cut_object` upgrade** — currently a Z plane only. The gizmo supports an
  arbitrary plane, keep-both, and dovetail/connector joints. Extend the existing
  tool; keep the current call shape working.

## Plan 4 — Creation and measurement

- **`measure_object`** — `namespace Measure` / `class Measuring`
  (`src/libslic3r/Measure.hpp:110`). Read-only: dimensions, and distances or angles
  between detected features. Useful to an agent for checking its own work, so
  prioritise it within this plan.
- **`emboss_text`** — text on a model, the `Emboss` gizmo's capability. Largest
  surface here (font selection, placement on a face, depth); scope it deliberately
  and say in the plan what is out of scope.
- **`emboss_svg`** — the `Svg` gizmo equivalent.

**Explicitly out of scope for this batch:** `assembly_view` and the manual
variable-layer-height painting (`layersediting`). Both are interaction/view
features with little agent value. `apply_adaptive_layer_height` already covers the
automatic case.
