# Batch 3 spec — feature selection for painting, and a server that stays responsive

The requirements for the third development batch. One plan implements this spec; it names this
file as its `**Spec:**`.

**Where the findings come from:** `2026-09-10-testing-session-bugs.md` in this directory,
items **T10** and **T11**, produced by painting a ComfyUI-generated figurine live with the user
on 2026-09-11. Read them — T11 carries the reproduction of "paint her bag blue" taking a ruler
and five renders, and T10 the three-minute paint that made the whole server unreachable.

**Decided with the user (2026-09-11):** build the see → point → fill loop so a feature can be
painted in one call, and stop heavy geometry from blocking the GUI thread.

## The problem, in one sentence each

**T11.** `paint_object` selects by band, box, sphere or whole volume; none of those names a
*feature*, so "paint the bag" costs a ruler-paint, three calibration renders and a box guess.

**T10.** On a 4.3-million-facet mesh a band paint took three minutes, during which the GUI
thread — and therefore every other tool — was unreachable, and the bridge reported a timeout for
an operation that then completed correctly.

## Requirements

### R1 — Seed fill: `paint_object` gains `selection: "connected"`

Paint the connected surface region reachable from a seed without crossing an edge sharper than
`angle` degrees. This is `TriangleSelector::seed_fill_select_triangles`
(`TriangleSelector.hpp:332`), which takes a mesh-local hit point, a facet index, a no-translation
transform, a clipping plane and the angle — no mouse anywhere in its signature.

- Seed given as `seed: {point: [x, y, z]}` in plate mm (snapped to the nearest surface point), or
  `seed: {volume_id, facet}` for a caller that already picked.
- `angle` optional, default **30** — the gizmo's own default (`GLGizmoPainterBase.hpp:279`).
- Works for all four modes; the state parameter is the same as for `box`.
- The response reports `seed` resolved (volume, facet, plate point) so a caller can see what was
  actually filled from.

### R2 — Components: `get_object_components` and `paint_object selection: "component"`

A generated or assembled model often has its feature as a separate shell. List the connected
components of each volume's mesh — id, facet count, area, plate bounding box — and let
`paint_object` paint one by id. Component ids are **deterministic** (discovery order by lowest
facet index) so an id read from `get_object_components` addresses the same shell in `paint_object`.

### R3 — Picking: `pick_facet`

Turn something an agent can see or name into a facet:

- by `point: [x, y, z]` — nearest surface point across the target volumes;
- by `ray: {origin, direction}` — first hit along the ray;
- by `pixel: [u, v]` + the `camera` object a render returned — the ray is unprojected server-side.

Returns the volume, facet, plate-frame point and normal, distance, and (optionally) the component
id. Pure geometry via `AABBMesh` (`libslic3r/AABBMesh.hpp`), testable without a GUI.

### R4 — Render metadata: `render_plate_view` returns its camera

Every view's result gains a `camera` object: the 4x4 view and projection matrices (16 numbers,
row-major), the viewport, the projection type, and `pixel_origin: "top_left"` (the saved image is
row-flipped from the GL buffer — `OrcaMCPPlateUtils.cpp:44,63`). A caller passes that object back
to `pick_facet` unchanged. This closes the loop: see → point → fill.

### R5 — Heavy geometry off the GUI thread

`paint_object`, `get_object_components` and `pick_facet` do their geometry on the calling HTTP
worker thread. The pattern is three hops:

1. main thread: resolve and validate the target, capture each volume's
   `std::shared_ptr<const TriangleMesh>` (`Model.hpp:861`), its plate transform, and identities
   (`ModelObject::id()`, `ModelVolume::id()`, the mesh pointer);
2. worker thread: compute the `FacetAssignment` (or components, or pick) against the captured
   immutable mesh;
3. main thread (mutating tools only): re-resolve, **verify identities still match**, take the
   snapshot, apply, refresh. If the scene changed underneath, return an error asking to retry
   rather than writing into a different mesh.

While a three-minute paint computes, `get_server_info` must answer.

### R6 — The cheap performance wins the review already named

- `facet_centroids` runs under `tbb::parallel_for` (the idiom at `CutSurface.cpp:811-818`).
- `selection: "all"` does not compute centroids (review M11).
- `paint_object`'s tool description states that very large meshes take time and that the bridge's
  `ORCAMCP_TIMEOUT` (default 120 s, `scripts/orcamcp-bridge.py:51`) may need raising.

### Acceptance

1. With the 4.3-million-facet figurine loaded: `pick_facet` by a plate point on its backpack, then
   `paint_object {selection: "connected", seed: {point}, filament}` paints the bag — verified by
   render — in **two calls**, no ruler.
2. While a 12-band paint runs on that mesh, a `get_server_info` call issued mid-paint returns in
   under two seconds.
3. A `render_plate_view` camera, fed to `pick_facet` with the pixel of a visible feature, returns
   a facet whose plate point lies on that feature.

### Explicitly out of scope

A brush / cursor selection (`select_patch` subdivides triangles — a much larger correctness
surface); an async job API with progress (R5 removes the blocking that motivated it; revisit if a
single call still exceeds the timeout after R5 and R6); caching the AABB tree between calls.
